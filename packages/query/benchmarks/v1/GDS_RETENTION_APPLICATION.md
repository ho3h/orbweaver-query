# Validate task retention on the original failed collaboration workload

After the 96-node diagnosis, run two new sequential native processes: the original
collaboration graph at one and four configured threads. Reuse each failed queue
condition's exact graph, 64 development sources, selected rich FastRP256 pipeline
with 16 negatives and unchanged classifier-selection budget. Keep the pinned
Neo4j/GDS 2026.09.0 binaries, ARM Java/Python runtime, 8 GiB heap, 900-second
transaction ceiling and existing numeric thread ceilings. Change task retention
to the explicit supported value of 60 seconds; leave the memory guard enabled.
The original failed cohort remains frozen and failed.

This is an instrumented resource/correctness diagnostic, not a replacement timing
campaign. Fit one model per thread condition and save its model-selection record
immediately. Stream and save complete native candidate scores, recompute exact
stable-ID top-16 independently, and compare all five partitioned requests with
that reference. Preserve all raw outputs, adaptive overfetch counters and failures.
Record differences from the failed condition's saved full scores; separately
fitted models, particularly at four threads, are not assumed identical.

After projection, fitting, the full-score reference and every repeated request,
record GDS memory detail/summary, active tasks, retained-task count and JVM heap
usage. Require zero task reservations and no active tasks at each completed-work
checkpoint. Read back the effective retention/progress settings. After the fifth
request, wait 65 seconds in intervals no longer than 30 seconds, then require
completed task records to have expired as well as reservations remaining zero.
Heap observations are samples, not a measurement of peak memory.

Use fresh output directories and source manifests. Keep process order one then
four threads explicit; no latency ratio or confidence interval is derived from
these diagnostic processes. Development quality is recomputed from saved scores
only to preserve the application contract; no configurations are tuned and no
confirmation inputs are opened. Even successful completion would establish only
this bounded native workload's behavior, not long-running stability, an Orbweaver
speedup or closure of the full application/1.0 gates.

Replay completed evidence without starting Neo4j:

```sh
python packages/query/benchmarks/v1/gds_retention_application_audit.py RUN
```

The audit requires both declared processes to have terminated successfully. It
reconstructs the undirected candidate domain directly from saved triples and
independently sorts the raw scores, checks every repeated output, recomputes
development metrics and prior-score differences, and reconciles memory details
with the summary at each checkpoint. File-integrity verification is separate.
